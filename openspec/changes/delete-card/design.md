## Context

Проект использует Vite + React + TypeScript на фронтенде. Данные доски хранятся в mock-базе json-server (`client/db.json`), к которой фронтенд обращается через Vite proxy (`/api` → `http://localhost:3001`). Реального Express-бэкенда пока нет (`server/` содержит только `.gitkeep` — реализация запланирована в теме 3 курса).

Состояние карточек управляется TanStack Query: `useQuery` с `queryKey: ["cards"]` в `App.tsx` загружает список, `useMutation` в `NewCardForm.tsx` создаёт карточки и инвалидирует кэш через `queryClient.invalidateQueries({ queryKey: ["cards"] })`.

Тип карточки определён в `client/src/types/card.ts`:
```typescript
type Card = { id: string; title: string; isDone: boolean; isUrgent?: boolean; };
```
Функции API определены в `client/src/api/cards.ts`: `fetchCards()` (GET) и `createCard(title)` (POST). Функции `deleteCard` не существует.

json-server автоматически поддерживает `DELETE /cards/:id` — это mock-сервер, а не реальный бэкенд.

## Goals / Non-Goals

**Goals:**
- Реализовать удаление карточки через UI с подтверждением.
- Добавить клиентскую API-функцию `deleteCard(id)`.
- Интегрировать удаление в существующий цикл TanStack Query.
- Обработать ошибки и отмену удаления.

**Non-Goals:**
- Реализация серверного бэкенда на Express — DELETE-эндпоинт json-server уже работает.
- Изменение типа `Card` — `id: string` уже есть.
- Bulk-удаление, drag-and-drop, архивирование.
- Оптимистичные обновления — используем стандартный подход с рефетчем.

## Decisions

### Decision 1: Где размещать кнопку удаления — в BoardCard или в BoardColumn

**Выбрано: в BoardCard.**

**Вариант A — кнопка в BoardCard (выбран):**
- Кнопка «×» рендерится внутри каждой карточки.
- `BoardCardProps` расширяется полями `id: string` и `onDelete: (id: string) => void`.
- `BoardColumn` пробрасывает `card.id` и `handleDelete(card.id)` в `BoardCard`.
- Плюсы: интуитивно понятно (кнопка удаления на самой карточке), соответствует паттернам Kanban-досок, минимальная связность — `BoardColumn` не знает о логике удаления.
- Минусы: `BoardCard` получает дополнительную зависимость `onDelete`.

**Вариант B — кнопка в BoardColumn:**
- `BoardColumn` рендерит обёртку с кнопкой удаления вокруг `BoardCard`.
- Плюсы: `BoardCard` остаётся чистым.
- Минусы: дополнительная обёртка в DOM, `BoardColumn` становится ответственным за логику удаления, нарушается принцип «компонент знает о своих действиях».

**Обоснование:** Вариант A лучше вписывается в текущую архитектуру. `BoardColumn` уже передаёт `card.id` как `key` — проброс `id` и `onDelete` как props естественное продолжение.

### Decision 2: Подтверждение удаления — `window.confirm` или кастомный диалог

**Выбрано: `window.confirm`.**

**Вариант A — `window.confirm` (выбран):**
- Простой нативный диалог браузера: «Удалить карточку "Название"?».
- Плюсы: ноль дополнительного кода, работает мгновенно, соответствует спецификации (требуется подтверждение).
- Минусы: нельзя стилизовать, нет анимации.

**Вариант B — кастомный модальный диалог:**
- Компонент `<ConfirmDialog>` с анимацией, стилизацией, кнопками «Удалить» / «Отмена».
- Плюсы: единый стиль с UI проекта, анимации.
- Минусы: требует создания нового компонента, дополнительного состояния (открыт/закрыт), стилей.

**Обоснование:** Для MVP-функционала `window.confirm` достаточен. Спецификация требует подтверждение, но не предписывает его реализацию. Кастомный диалог можно добавить позже как улучшение.

### Decision 3: Стандартный подход с рефетчем вместо оптимистичного обновления

**Выбрано: стандартный подход (отправка → успех → invalidate → рефетч).**

**Вариант A — стандартный (выбран):**
- После `deleteCard(id)` вызываем `queryClient.invalidateQueries({ queryKey: ["cards"] })` в `onSuccess`.
- Плюсы: просто, надёжно, данные всегда синхронизированы с сервером.
- Минусы: кратковременная задержка между удалением и исчезновением карточки (один рефетч).

**Вариант B — оптимистичное обновление:**
- Карточка мгновенно убирается из UI, запрос отправляется в фоне.
- При ошибке — карточка возвращается.
- Плюсы: мгновенный отклик UI.
- Минусы: сложнее, требует `onMutate`/`onError`/`onSettled`, риск рассинхрона.

**Обоснование:** Удаление — не частая операция. Задержка в один рефетч (50–200 мс) незаметна. Стандартный подход проще и надёжнее.

## Путь операции удаления

```
1. Пользователь нажимает кнопку удаления (×) на карточке (BoardCard)
   ↓
2. Вызывается window.confirm("Удалить карточку «{title}»?")
   ↓
   └─ ОТМЕНА → диалог закрывается, ничего не происходит
   ↓
3. ПОДТВЕРЖДЕНИЕ → BoardCard вызывает onDelete(card.id)
   ↓
4. BoardColumn передаёт вызов в mutation-хук deleteCardMutation
   ↓
5. deleteCard(id) из api/cards.ts отправляет DELETE /api/cards/:id
   ↓
   └─ ОШИБКА → onError → alert("Не удалось удалить карточку")
   ↓
6. УСПЕХ → onSuccess → queryClient.invalidateQueries({ queryKey: ["cards"] })
   ↓
7. React Query автоматически рефетчит список → BoardColumn получает обновлённый список
   ↓
8. Карточка исчезает из UI
```

## Обработка ошибок

Реализуется через `useMutation` опцию `onError`:

```typescript
const deleteMutation = useMutation({
  mutationFn: (id: string) => deleteCard(id),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["cards"] });
  },
  onError: () => {
    alert("Не удалось удалить карточку");
  },
});
```

- При сетевой ошибке или ответе сервера 4xx/5xx — `onError` с `alert`.
- Карточка остаётся на доске (состояние не меняется).
- `window.confirm` гарантирует, что запрос уходит только по явному подтверждению пользователя.

## API-слой

Функция `deleteCard` будет добавлена в `client/src/api/cards.ts`:

```typescript
export async function deleteCard(id: string): Promise<void> {
  const response = await fetch(`/api/cards/${id}`, { method: "DELETE" });
  if (!response.ok) throw new Error("Не удалось удалить карточку");
}
```

**Важно:** url `/api/cards/:id` — это стандартный REST-паттерн json-server. Реальный бэкенд на Express должен будет реализовать `DELETE /cards/:id` для соответствия.

## Риски / Trade-offs

| [Risk] | [Митигация] |
|--------|-------------|
| Реальный бэкенд (Express) не реализует `DELETE /cards/:id` | Функция `deleteCard` уже готова. При переходе на Express достаточно добавить роутер — фронтенд не изменится. |
| Быстрый двойной клик по кнопке удаления | `mutation.isPending` блокирует повторный вызов (как в `NewCardForm`). |
| Удаление карточки, которой уже нет на сервере (404) | `onError` покажет alert — пользователь узнает о проблеме. |
| Рассинхрон при параллельных операциях (создание + удаление) | TanStack Query гарантирует последовательную инвалидацию кэша. |
